# Blueprint — ADR-0142.1: CI Flows & Workflow Utilities as Individual Files

> Referência: [ADR-0142.1](./ADR-0142.1.md) · Parent: [ADR-0142 (DSG, Implementado)](./ADR-0142.md)

> **Status:** **Implementado** (2026-07-08). **Arquivado** em `docs/adr/archive/ADR-0142.1-BP.md`.

> **Desambiguação de sigla:** `BP` = **Blueprint** (este arquivo), **não** "Best Practice". Best Practices da stack = DSG Vol 8 (BP-001…BP-007). O conjunto ADR segue o padrão do skill `adr-generator`: `ADR-XXX.md` + `ADR-XXX-BP.md` + `ADR-XXX-TODO.md`.

---

## 1. Visão Geral

### Objetivo
Tornar cada workflow e fluxo CI do DSG um arquivo utilitário individual, atômico, componível e versionável em `docs/kilosettings/ci-workflows/`, de modo que agentes e subagentes possam consumi-los diretamente como contrato de execução.

### Métricas de Sucesso

| Métrica | Antes | Depois | Status |
|---------|-------|--------|--------|
| Tempo para um agente obter um fluxo completo | grep em 440 linhas | 1 arquivo focal | ⬜ |
| Contrato passável a subagente | copiar trecho manual | arquivo inteiro | ⬜ |
| Deriva narrativa↔executável | não detectada | detectável por link `source` | ⬜ |
| Versionamento por fluxo | diff do volume inteiro | diff por arquivo | ⬜ |

Convenção de nome: `wf-<kebab-id>.md` para workflows; `ci-<kebab-id>.md` para fluxos CI.

## 3. Frontmatter Contract (obrigatório)

Todo arquivo utilitário DEVE iniciar com:

```yaml
---
id: wf-implement-adr
title: Workflow — Implement ADR
type: workflow            # workflow | ci-flow
version: 1.0.0            # semver
status: active            # active | deprecated
trigger: "ADR status = Accepted"
participants: [implementation, writing-plans, code, testing, code-review, documentation]
related_skills: [implementation, writing-plans, testing, code-review, documentation]
related_bp: [ADR-0142.1-BP]
source: docs/dsg/volume-7/workflow-cookbook.md#workflow-1-implement-adr
---
```

| Campo | Obrigatório | Descrição |
|-------|-------------|-----------|
| `id` | ✅ | kebab-case único, igual ao nome do arquivo sem extensão |
| `title` | ✅ | título legível |
| `type` | ✅ | `workflow` ou `ci-flow` |
| `version` | ✅ | semver; bumpar em toda mudança |
| `status` | ✅ | `active` ou `deprecated` |
| `trigger` | ✅ | condição de ativação |
| `participants` | ✅ | agentes/skills envolvidos |
| `related_skills` | ✅ | skills da stack usadas |
| `related_bp` | ✅ | ADR/BP de origem |
| `source` | ✅ | link para a seção do DSG (anti-deriva) |

## 4. Template Canônico de Arquivo Utilitário

```markdown
---
<frontmatter do item 3>
---

# <tipo>: <nome>

## Goal
<objetivo de uma linha>

## Preconditions
- [ ] <condição>

## Inputs
- <entrada>

## Sequence
1. <passo>  (idempotente; documentar check de estado se relevante)

## Validation Gates
| Gate | Checks | Pass Criteria |
|------|--------|---------------|

## Rollback
<procedure>  (todo workflow TEM rollback; todo ci-flow TEM fail policy)

## Exit Criteria
- [ ] <critério>

## Metrics
- <métrica>

## Source Reference
DSG Vol 7, Workflow N — docs/dsg/volume-7/workflow-cookbook.md
```

Para `ci-flow`, a seção **Validation Gates** inclui coluna de **Enforcement** (`local` / `pipeline`) e o **Rollback** declara a política **fail-open** ou **fail-closed**.

## 5. Regra de Sincronia (Fonte Única de Verdade)

```
Arquivo utilitário (docs/kilosettings/ci-workflows/*.md)  = FONTE CANÔNICA
DSG Vol 7 (narrativa)                                      = PONTEIRO (linka p/ utilitário)
```

- Editar um fluxo ⇒ editar o **arquivo utilitário**; DSG Vol 7 recebe apenas ponteiro/link.
- Nunca editar só a narrativa. O `source` no frontmatter é o checkpoint de deriva.
- `INDEX.md` é o ponteiro mestre; deve listar todos os utilitários com status.

---

## 6. Conceitos Fundamentais

### 6.1 Atomicidade
O arquivo deve ser utilizável com zero contexto externo. Quem lê só ele entende goal, precondições, sequência, gates, rollback, exit.

### 6.2 Componibilidade
Um subagente que recebe o arquivo deve saber: o que ele possui (ownership), o que NÃO deve fazer (forbidden), o que escalar (escalation).

### 6.3 Idempotência
Passos da sequência devem ser re-executáveis sem efeito colateral duplicado. Documentar checks de estado.

### 6.4 Versionamento
Bump `version` (semver) em qualquer mudança. PR de mudança requer revisão; item de TODO associado.

## 7. Workflow de Extração

```
1. Ler seção-alvo no DSG Vol 7
2. Criar arquivo utilitário com frontmatter + template canônico
3. Migrar conteúdo narrativo → estrutura canônica
4. Substituir seção no DSG Vol 7 por ponteiro (link) ao utilitário
5. Registrar no INDEX.md
6. Marcar item no ADR-0142.1-TODO como Concluído
```

## 8. Anti-patterns

### 🔴 Crítico
#### Editar só a narrativa (DSG) e esquecer o utilitário
**Por que é ruim:** cria deriva; agentes consomem versão desatualizada.
**Como evitar:** fonte canônica = utilitário; DSG é ponteiro. Checkpoint = `source` no frontmatter bate com a seção.

#### Utilitário sem frontmatter
**Por que é ruim:** não é descoerto nem versionável nem linkável.
**Como evitar:** BP item 3 é mandatório; CI/checklist rejeita arquivo sem frontmatter.

### 🟡 Médio
#### Passo não-idempotente
**Por que é ruim:** re-execução corrompe estado.
**Como evitar:** documentar check de estado em cada passo mutável.

#### Rollback ausente
**Por que é ruim:** falha sem rota de recuperação.
**Como evitar:** todo workflow tem rollback; todo ci-flow tem fail policy.

## 10. Edge Cases

### Novo workflow adicionado à stack
**Situação:** surge um 9º workflow não previsto em ADR-0142.
**Solução:** criar `wf-<id>.md` seguindo o Blueprint; adicionar ao INDEX; DSG Vol 7 ganha ponteiro. Nenhuma mudança de ADR necessária (Blueprint já prevê extensão).

### Workflow deprecado
**Situação:** fluxo obsoleto.
**Solução:** `status: deprecated` no frontmatter; INDEX marca; DSG Vol 7 mantém ponteiro com nota de deprecação. Não deletar (histórico de auditoria).
